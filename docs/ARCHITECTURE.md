## Путь данных

1. HTTP-хост читает тело порциями, считает SHA-256 исходных байтов и временно буферизует файл на диске. `Imports__SpoolDirectory` задаёт каталог. Файл удаляется при закрытии. Защита диска от большого числа параллельных загрузок требует лимитов шлюза или квоты среды.
2. EF Core обслуживает каталог, версии договоров, историю импорта и список usage. Начальная миграция использует версионированный DDL из `schema.sql`. Управление миграциями отделено от запуска HTTP-хоста.
3. Npgsql Binary COPY записывает валидные строки во временную таблицу. SQL сопоставляет треки, выбирает первый подходящий EventId внутри файла и пропускает существующие события. Для начислений фиксируется соответствие добавленных событий версиям договоров одним SQL-запросом. По 500 событий за итерацию загружаются в доменный калькулятор, начисления записываются бинарным COPY. Доступные через API версии и их доли неизменяемы после создания.
4. Dapper строит отчёт за период параметризованным запросом. Прослушивания и начисления агрегируются отдельно, чтобы одна запись usage с несколькими правообладателями учитывалась в числе прослушиваний один раз.

## Индексы

- `usage_records(event_id)` обеспечивает глобальную уникальность и быстрый конфликт при вставке.
- `(usage_date DESC, event_id DESC)` обслуживает диапазон по дате и стабильный порядок выдачи, `(track_id, usage_date DESC, event_id DESC)` — ту же выборку для одного трека.
- `(import_id, event_id)` ускоряет поиск новых событий для расчёта. PK начислений начинается с `event_id` для подсоединения к периоду использования.
- Уникальный `usage_imports(sha256)` сериализует повторы одного файла. `(created_at DESC, id DESC)` задаёт стабильный порядок списка.
- GiST ограничение на `track_id` и `daterange` предотвращает пересечения контрактов и поддерживает сопоставление по дате. B-tree индекс по треку обслуживает его FK. Другие индексы FK покрывают ссылки на каталог и доли.

[performance.sql](performance.sql) содержит `EXPLAIN (ANALYZE, BUFFERS)` для характерных запросов. Планы зависят от объёма, распределения дат и статистики. Большие OFFSET и широкие аналитические диапазоны требуют измерений перед использованием под нагрузкой.

## План партиционирования

Кандидат на будущий этап — диапазоны по месяцу `usage_date`. PostgreSQL требует включать ключ партиционирования в ограничение уникальности партиционированной таблицы. Ограничение `(event_id, usage_date)` допускает один EventId в разных месяцах. Для глобальной уникальности потребуется непартиционированный реестр EventId с PK, сохранение его в той же транзакции и пересмотр FK из начислений. Оценить конкурентные вставки, удаление партиций, миграцию и стоимость дополнительного индекса. Текущая таблица остаётся непартиционированной.
